Design Study

Three directions for the Details page

These prototypes respond to the same product problem: the current UI mixes report usage, model retention reasons, heavy technical views, and cleanup actions in one surface. The proposals below separate those concerns in three different ways.

Goal: public-ready Details page No backend wiring yet Static prototypes only

Quick recommendation

If the next release needs one safe direction, start from Proposal 1. Proposal 3 is a strong follow-up if the product should become more cleanup-oriented. Proposal 2 is best kept in beta.

  • Proposal 1: Evidence FirstBest public candidate. Clean split between report usage and model-only retention.
  • Proposal 2: Split WorkspaceMore ambitious analytical view with grouped sections and a stronger inspector.
  • Proposal 3: Review QueueCleanup-first layout organized around decisions and queues, not one giant table.

Comparison

Proposal Main idea Best for Biggest strength Main risk
1. Evidence First Keep a table, but explicitly separate report usage from model-only retention and indirect dependencies. Stable/public release Most understandable for new users Still table-driven, so it can feel conventional if not polished well
2. Split Workspace Turn the page into a richer analytical workspace with grouped sections and an inspector. Beta / internal exploration Best explanatory power Can become too dense for large models
3. Review Queue Reframe the page as a cleanup workbench with queues, actions, and decision support. Action-heavy cleanup workflows Most purpose-built for the tool's core job Less useful for pure exploration and lineage browsing

All three intentionally remove the idea that top-level `Item Details` and `Table Details` should be separate tabs. In every proposal, details behave like drill-through or inspector content instead.
